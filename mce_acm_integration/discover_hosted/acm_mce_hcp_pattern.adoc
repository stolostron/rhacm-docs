= {hcp} fleet management architecture pattern
//location and title up for discussion--since we cannot keep adding the the overview, maybe it is better to rename this folder to acm_mce_hosted_clusters, if all that in it applies. We seem to, however, need an HCP space now.

As your {hcp} deployment scales, you can strategically manage resource requirements and maintain centralized visibility across your fleet. Consider the following guidance for an architecture pattern for managing {hcp} clusters at scale.

{acm} or {mce} enables {hcp} capabilities. While deployments often begin with a single hub cluster, scaling the number of {hcp} clusters introduces several challenges, such as the following examples:

* *Resource consumption:* Resource requirements grow proportionally with the number of planes.
* *Scaling complexity:* You must choose between scaling existing clusters or provisioning new ones.
* *Management overhead:* Managing multiple hosting clusters individually becomes complex.
* *Visibility gaps:* Maintaining centralized visibility and governance across disparate clusters is difficult.

To address these challenges, implement a _hierarchical management pattern_, which is an architecture that separates the management logic from the hosting infrastructure. Learn more about this pattern in the sections that follow.

Learn about the benefits of this architecture pattern in the following table:

.Advantages of the hierarchical management pattern
[cols="1,3", options="header"]
|===
| Benefit | Description
| Centralized management | Provides a single pane of glass for the entire fleet.
| Scalability | Allows you to add {mce-short} clusters as needed to increase capacity.
| Resource optimization | Focuses {mce-short} clusters on hosting and the {acm-short} hub cluster on management.
| Operational efficiency | Enables unified policy management and governance.
| Cost effectiveness | Allows you to right-size each component for a specific role.
|===

== Central {acm-short} hub cluster

The central {acm-short} hub cluster serves as the primary management and visibility layer for the following functions:

* Provides a single console for end-to-end fleet management
* Manages operational policies across the entire infrastructure
* Enables comprehensive monitoring and governance capabilities

== {mce-short} hosting infrastructure

Deploy multiple {mce-short} clusters to serve as the physical hosting infrastructure for control planes. See the following functions of the {mce-short} hosting cluster:

* Provides {hcp} components with a smaller footprint than a full {acm-short} installation.
* Includes the management console and BareMetal infrastructure operators.
* Optimizes for hosting workloads rather than high-level fleet management.

== Implementation considerations

* The central {acm-short} hub cluster manages both the {mce-short} clusters and the attached {hcp} clusters
* Policies and governance are applied consistently across the entire infrastructure.
* Monitoring and alerting are centralized while hosting capacity remains distributed.

See the following process overview:

* *Deploy the central {acm-short} hub cluster:* Establish this cluster as your primary management interface.
* *Deploy {mce-short} clusters:* Use these as the hosting infrastructure for your control planes.
* *Configure discovery:* Ensure the {acm-short} hub cluster can manage both the {mce-short} clusters and the attached {hcp} clusters.

*Important:* A {acm-short} cluster cannot manage another {acm-short} cluster.

If you have already deployed multiple {acm-short} hub clusters to host control planes, use the following process to adopt the recommended pattern:

* *Convert {acm-short} hosting clusters to {mce-short}:* Uninstall {acm-short} and install {mce-short} on the clusters that are designated for hosting infrastructure.
* *Preserve {hcp} clusters:* Ensure the conversion process does not disrupt existing {hcp} clusters.
* *Designate the hub cluster:* Select one {acm-short} cluster to serve as the central management hub cluster.
