= Implementing fine-grained role-based access control with the console (Technology Preview*)

{acm} supports fine-grained role-based access control (RBAC). As a cluster administrator, you can manage and control permissions at the namespace level on managed clusters, rather than at the cluster level. Grant permissions to a namespace without granting permission to the entire managed cluster, or virtual machine, to further secure your clusters.

*Required access:* Cluster administrator

To learn about {ocp-short} default and virtualization roles and permissions, see link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.17/html/virtualization/about#authorization_virt-security-policies[Authorization] in the {ocp-short} documentation.

See xref:../secure_cluster/rbac_implement_rhacm.adoc#rhacm-rbac-implement[Implementing role-based access control] for more details about {acm-short} role-based access.

.Prerequisites

See the following requirement to manage fine-grained role-based access control:

. In your `MultiClusterHub` custom resource `spec.overrides.components` field, set `fine-grained-rbac-preview` to `true` to enable the feature.
. In your `MultiClusterHub` custom resource `spec.overrides.components` field, set `search` to `enabled` to retrieve a list of managed clusters namespaces that can represent virtual machines that are used for access control.
. Ensure you have virtual machines by creating or migrating them on the hub cluster.
. Verify that the `ClusterPermission` resource is created and is in ready status.
. You need to install policies on hub cluster to access the `kubevirt` roles.

== Assigning fine-grained role-based access control in the console

*Technology Preview:* You can assign users to manage virtual machines with fine-grained role-based access control. Action are disabled in the console if the user-role access is not permitted.

You can grant access to the following roles for {ocp-virt-short}, which are extensions of the default roles:

- `kubevirt.io:view`: only view resources
- `kubevirt.io:edit`: modify resources
- `kubevirt.io:admin`: view, modify, delete resources; grant permissions

. As a cluster administrator, click *Access control* > *Create permission* in the console.
. *Optional:* Slide the *YAML* option on to see the metadata that you enter populate in the *Access Control YAML* window.
. In the _Basic information_ window, add the information for your cluster permission, such as the cluster and the user or group. Choose the cluster or virtual machine with the specific namespace for that user permission.
. Add the `Role bindings` information, which sets permissions at the namespace level. Add namespaces in the cluster or virtual machine, users or groups, and roles, such as `kubevirt.io:view`, for fine-grained role-based access control. You can choose a combination of `RoleBindings`.
. Add the `Cluster role binding` with the same information to set permissions at the cluster level. 
+
*Note:* As an administrator, you need to add either `Role bindings` or `Cluster role binding` for a valid `ClusterPermission`. You can also choose to add both. One cluster permission is used for each managed cluster.
. Review and click *Create permission*.
. Check for a `Ready` status in the console, though for the Technology Preview, you might not see a valid status for all possible `ClusterPermissions` combinations. 
. Click *Edit permission* to edit the `Role bindings` and `Cluster role binding`.
. *Optional:* Click *Export YAML* to use the resources for GitOps or in the terminal.
. You can delete the `ClusterPermissions` resource when you are ready.
