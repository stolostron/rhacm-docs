[#uninstall-manual-remove-cr]
== Uninstalling and reinstalling earlier versions with an upgrade can fail

Uninstalling {acm-short} from {ocp-short} can cause issues if you later want to install earlier versions and then upgrade. For instance, when you uninstall {acm-short}, then install an earlier version of {acm-short} and upgrade that version, the upgrade might fail. The upgrade fails if the custom resources were not removed.

Follow the link:../install/cleanup_reinstall.adoc#cleanup-reinstall[Cleaning up artifacts before reinstalling] procedure to prevent this problem.

link:https://issues.redhat.com/browse/ACM-14343[ACM-14343]

[#add-on-stuck-upgrade]
== The _kubevirt-hyperconverged_ add-on is stuck in `in progress` status during upgrade from {acm-short} {product-version-prev} to {product-version}

During an upgrade from {acm-short} {product-version-prev} to {product-version}, the `kubevirt-hyperconverged-operator` resource is not cleaned up and you receive the following error in the `ManifestWork` resource:

[source,bash]
----
Failed to apply manifest: operatorpolicies.policy.open-cluster-management.io
"kubevirt-hyperconverged-operator" is forbidden: User
"system:serviceaccount:open-cluster-management-agent:klusterlet-work-sa"
cannot get resource "operatorpolicies" in API group
"policy.open-cluster-management.io" in the namespace "open-cluster-management-policies"
----

To resolve the issue, complete the following steps:

. Remove existing resources. Run the following commands:

+
[source,bash]
----
oc delete clustermanagementaddon kubevirt-hyperconverged-operator --ignore-not-found

oc delete addontemplate kubevirt-hyperconverged-operator --ignore-not-found
----

. Get the namespace that is specified in the `installer.namespace` label of the `kubevirt-hyperconverged` `ClusterManagementAddOn` resource. Run the following command and record the output to use in step 4:

+
[source,bash]
----
oc get clustermanagementaddon kubevirt-hyperconverged -o jsonpath='{.metadata.labels.installer\.namespace}'
----

. Delete the previous `ClusterManagementAddOn` resource, which is version `v1alpha1`. Run the following command:

+
[source,bash]
----
oc delete clustermanagementaddon kubevirt-hyperconverged
----

. Create the `ClusterManagementAddOn` resource. See the following example and replace `<installer_namespace>` with the value that you retrieved in the previous step:

+
[source,yaml]
----
apiVersion: addon.open-cluster-management.io/v1beta1
kind: ClusterManagementAddOn
metadata:
  name: kubevirt-hyperconverged
  annotations:
    addon.open-cluster-management.io/lifecycle: "addon-manager"
spec:
  addOnMeta:
    description: Kubevirt Hyperconverged
    displayName: Kubevirt Hyperconverged
  defaultConfigs:
    - group: addon.open-cluster-management.io
      resource: addontemplates
      name: kubevirt-hyperconverged
  installStrategy:
    type: Placements
    placements:
    - name: openshift-cnv
      namespace: <installer_namespace>
----

. Run the following command to apply your resource:

+
[source,bash]
----
oc apply -f <filename.yaml
----

link:https://issues.redhat.com/browse/ACM-31036[ACM-31036]

[#siteconfig-stale-neighbor-cache]
== Managed cluster fails to rejoin the hub cluster after server replacement with Image-Based Break/Fix

After a bare-metal server replacement by using Image-Based Break/Fix (IBBF) or the cluster reinstallation feature of the {sco}, the managed cluster might fail to rejoin the hub cluster. This issue occurs because the hub cluster node that hosts the API VIP retains a stale neighbor cache entry that maps the spoke cluster IP address to the MAC address of the old server. The replacement server uses the same IP address but has a different MAC address, which causes the hub cluster to send reply packets to the wrong Layer 2 address.

The klusterlet agent logs on the spoke cluster show repeated timeout errors similar to the following message:

[source,text]
----
dial tcp <hub-api-address>:6443: i/o timeout
----

The {sco} reimport process loops indefinitely because the spoke cluster never becomes healthy.

To work around this issue, flush the stale neighbor cache entry on the hub cluster node that hosts the API VIP. Complete the following steps:

. Identify the hub cluster node that is running the API VIP.

. Verify that a stale neighbor cache entry exists on the hub cluster node by running the following command. Replace `<spoke-ip-address>` with the IP address of the spoke cluster and `<bridge-interface>` with the network bridge interface name on the hub cluster node:

+
[source,bash]
----
sudo ip neigh show to <spoke-ip-address> dev <bridge-interface>
----

. Delete the stale neighbor cache entry by running the following command:

+
[source,bash]
----
sudo ip neigh del <spoke-ip-address> dev <bridge-interface>
----

. Verify that the managed cluster status changes to `Available` by running the following command. Replace `<cluster-name>` with the name of your managed cluster:

+
[source,bash]
----
oc get managedcluster <cluster-name>
----
