=== Cluster API Provider Metal3 certificate generation fails after upgrade

After you upgrade from {mce} version 2.10 or 2.10.1 to version 2.11, the automatic generation of certificates for the Cluster API Provider Metal3 webhooks fail due to a naming conflict in the target resources. As a result, webhooks do not validate.

To resolve the issue, manually delete the existing secret and the renamed service. The operator then regenerates the correct secret.

Complete the following steps on your managed cluster:

. Delete the webhook service. Run the following command:

+
[source,bash]
----
oc delete service capm3-webhook-service -n multicluster-engine
----

. Delete the Transport Layer Security (TLS) secret. Run the following command:

+
[source,bash]
----
oc delete secret capm3-webhook-service-cert -n multicluster-engine
----

. Clear the error annotations. Run the following command:

+
[source,bash]
----
oc annotate service mce-capm3-webhook-service -n multicluster-engine \
service.alpha.openshift.io/serving-cert-generation-error- \
service.alpha.openshift.io/serving-cert-generation-error-num- \
service.beta.openshift.io/serving-cert-generation-error- \
service.beta.openshift.io/serving-cert-generation-error-num-
----

. Delete the stale webhook configurations. Run the following commands:

+
[source,bash]
----
oc delete mutatingwebhookconfiguration capm3-mutating-webhook-configuration
----

+
[source,bash]
----
oc delete validatingwebhookconfiguration capm3-validating-webhook-configuration
----

. Delete the new TLS secret. Run the following command:

+
[source,bash]
----
oc delete secret mce-capm3-webhook-service-cert -n multicluster-engine
----

. Restart the pod to regenerate the certificate. Run the following command:

+
[source,bash]
----
oc delete pod mce-capm3-controller-manager-<hash> -n multicluster-engine
----

. Delete the old `controller-manager` deployment. Run the following command:

+
[source,bash]
----
oc delete deployment capm3-controller-manager -n multicluster-engine
----

+
[source,bash]

oc get mce multiclusterengine -o json | \
  jq -r '.spec.overrides.components[] | select(.name | contains("cluster-api"))'

+
[source,bash]

+
[source,bash]

oc annotate mce multiclusterengine force-reconcile=$(date +%s) --overwrite
----

=== Resource deletion during cluster distribution updates

When a change occurs in the cluster because of the `Placement` resource, cluster redistribution occurs across multiple `PlacementDecisions` resources. During the sequential update, a cluster is temporarily missing from all `PlacementDecisions` resources.

Controllers that monitor `PlacementDecisions` resources identify this temporary deletion as cluster removal. This sequence leads to unnecessary resource deletion and recreation. For example, the `addon-management-controller` deletes and re-creates `ManagedClusterAddOns`, which cause workload disruption.

[#hypershift-infra-node-config]
=== HyperShift operator does not receive infrastructure node configuration

When {acm-short} or {mce-short} is installed with infrastructure node selection configured, by using `nodeSelector` and `tolerations` for infrastructure node, the HyperShift operator deployment does not receive the settings. 

Even if the `multicluster engine` subscription is configured to place pods on infrastructure nodes by using `nodeSelector` and `tolerations`, the HyperShift operator pods are scheduled on regular worker nodes instead of the designated infrastructure nodes.

The HyperShift operator deployment does not automatically propagate the infrastructure node placement configuration from the subscription.

After you install the HyperShift add-on, manually patch the HyperShift operator deployment to add the infrastructure node selector and tolerations. See the following example:

[source,yaml]
----
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
----

To resolve the problem, apply a patch to the operator deployment in the `hypershift` namespace by running the following command with the specifications for your infrastructure nodes:

[source,bash]
----
oc patch deployment operator -n hypershift --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"node-role.kubernetes.io/infra":""},"tolerations":[{"key":"node-role.kubernetes.io/infra","operator":"Exists","effect":"NoSchedule"}]}}}}'
----

The manual patch ensures that the operator pods are placed on the correct nodes to comply with your infrastructure requirements.

link:https://issues.redhat.com/browse/ACM-24191[ACM-24191]

[#hcp-fails-rosa]
=== HyperShift installation fails on {rosa} due to admission webhook error

When you install {mce} 2.10 on {rosa}, the HyperShift installation job might fail repeatedly with an admission webhook error similar to the following message: `namespace-validation.managed.openshift.io denied the request`. See the following explanations for the error:

* The installation process attempts to create a `hypershift` namespace that includes the `openshift.io/cluster-monitoring: "true"` label. 

* The {rosa} managed admission webhooks prevent users from modifying protected labels on namespaces, including the `cluster-monitoring` label.

* The platform monitoring flag defaults to monitoring the operator, which adds the `cluster-monitoring` label to the `hypershift` namespace. 

* In managed environments, such as {rosa}, the service provider typically handles platform-level monitoring. Therefore, this monitoring is not required and conflicts with namespace protection policies.

To resolve this issue, create a `ConfigMap` in the `local-cluster` namespace to disable platform monitoring by following these steps:

. Create a YAML file for the `ConfigMap` with the following content:

+
[source,yaml]
----
kind: ConfigMap
apiVersion: v1
metadata:
  name: hypershift-operator-install-flags
  namespace: local-cluster
data:
  installFlagsToAdd: "--platform-monitoring=None"
  installFlagsToRemove: ""
----

. Apply the `ConfigMap` to your cluster. Run the following command, replacing `<filename>` with the name of your YAML file:

+
[source,bash]
----
oc apply -f <filename>.yaml
----

This configuration instructs the HyperShift installer to skip the `cluster-monitoring` label, which avoids the admission webhook conflict.

[#client-cannot-reach-ipxe-script]
=== Client cannot reach iPXE script

iPXE is an open source network boot firmware. See link:https://ipxe.org/[iPXE] for more details.

When booting a node, the URL length limitation in some DHCP servers cuts off the `ipxeScript` URL in the `InfraEnv` custom resource definition, resulting in the following error message in the console:

`no bootable devices`

To work around the issue, complete the following steps:

. Apply the `InfraEnv` custom resource definition when using an assisted installation to expose the `bootArtifacts`, which might resemble the following file:

[source,yaml]
----
status:
  agentLabelSelector:
    matchLabels:
      infraenvs.agent-install.openshift.io: qe2
  bootArtifacts:
    initrd: https://assisted-image-service-multicluster-engine.redhat.com/images/0000/pxe-initrd?api_key=0000000&arch=x86_64&version=4.11
    ipxeScript: https://assisted-service-multicluster-engine.redhat.com/api/assisted-install/v2/infra-envs/00000/downloads/files?api_key=000000000&file_name=ipxe-script
    kernel: https://mirror.openshift.com/pub/openshift-v4/x86_64/dependencies/rhcos/4.12/latest/rhcos-live-kernel-x86_64
    rootfs: https://mirror.openshift.com/pub/openshift-v4/x86_64/dependencies/rhcos/4.12/latest/rhcos-live-rootfs.x86_64.img
----

. Create a proxy server to expose the `bootArtifacts` with short URLs.

. Copy the `bootArtifacts` and add them to the proxy by running the following commands:

+
----
for artifact in oc get infraenv qe2 -ojsonpath="{.status.bootArtifacts}" | jq ". | keys[]" | sed "s/\"//g"
do curl -k oc get infraenv qe2 -ojsonpath="{.status.bootArtifacts.${artifact}}"` -o $artifact 
----

. Add the `ipxeScript` artifact proxy URL to the `bootp` parameter in `libvirt.xml`.

[#assisted-incorrect-cached-image-disconnected]
=== {ai} pulls incorrect cached image in disconnected environments

In a disconnected environment, {ai} might pull an incorrect cached release image instead of the image from your disconnected registry.

To work around the issue, prevent the `cluster-image-set-controller` from recreating the `ClusterImageSet` resources during deletion and delete the `ClusterImageSet` resources on the hub cluster to clear the hub cluster image cache. . Create a `ConfigMap` that points the controller to a Git repository that does not exist. Run the following command:

+
[source,bash]
----
oc create configmap cluster-image-set-git-repo -n multicluster-engine \
  --from-literal=gitRepoUrl=https://github.com/stolostron/does-not-exist.git \
  --from-literal=channel=fast \
  --dry-run=client -o yaml | oc apply -f -
----

. Delete the `ClusterImageSet` resources on the hub cluster to clear the hub cluster image cache. Run the following command:

+
[source,bash]
----
oc delete clusterimagesets --all --ignore-not-found=true --wait=true --timeout=5m
----

=== Managed cluster fails to rejoin the hub cluster after server replacement with Image-Based Break/Fix

After a bare-metal server is replaced by using Image-Based Break/Fix, or the cluster reinstallation feature of the {sco}, the managed cluster might fail to rejoin the hub cluster. 

This issue occurs because the hub cluster node that hosts the API VIP retains a stale neighbor cache entry that maps the managed cluster IP address to the MAC address of the previous server. 

The replacement server uses the same IP address, but has a different MAC address, which causes the hub cluster to send reply packets to the wrong Layer 2 address.

The klusterlet agent on the managed cluster display logs repeated timeout errors similar to the following message:

[source,bash]
----
dial tcp <hub-api-address>:6443: i/o timeout
----

The {sco} reimport process loops indefinitely because the managed cluster never becomes healthy. 

To work around this issue, flush the stale neighbor cache entry on the hub cluster node that hosts the API VIP. Complete the following steps:

. Identify the hub cluster node that is running the API VIP.

. Verify that a stale neighbor cache entry exists on the hub cluster node by running the following command. Replace `<spoke-ip-address>` with the IP address of the managed cluster and `<bridge-interface>` with the network bridge interface name on the hub cluster node:

+
[source,bash]
----
sudo ip neigh show to <spoke-ip-address> dev <bridge-interface>
----

. Delete the stale neighbor cache entry by running the following command:

+
[source,bash]
----
sudo ip neigh del <spoke-ip-address> dev <bridge-interface>
----

. Verify that the managed cluster status changes to `Available` by running the following command. Replace `<cluster-name>` with the name of your managed cluster:

+
[source,bash]
----
oc get managedcluster <cluster-name>
----
