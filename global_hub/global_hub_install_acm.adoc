= Installing {global-hub} on an existing {acm-short} hub cluster

You can install {global-hub} in an existing {acm-short} hub cluster and enable the {global-hub} agent in {acm-short}. Learn about the following capabilities: 

* When you install {global-hub} in an {acm-short} hub cluster, Kafka receives the information from the {global-hub} operator and stores it in the {global-hub} database, giving you access to the clusters, policies, and events. 
* Kafka stores the {global-hub} operator information, so as a Kafka consumer, you can access other components. For example, you can integrate with Red Hat Advanced Cluster Security and Red Hat Event-Driven Ansible. 
* Your data is stored in the {global-hub} database so you can view the cluster and policy information in the Grafana dashboards. 

To install {global-hub} on an existing {acm-short} hub cluster, you must set the `installAgentOnLocal` field to `true` by applying the following YAML sample:

[source,yaml]
----
apiVersion: operator.open-cluster-management.io/v1alpha4
kind: MulticlusterGlobalHub
metadata:
  name: multiclusterglobalhub
  namespace: multicluster-global-hub
spec:
  enableMetrics: true
  installAgentOnLocal: true  <1> 
  dataLayer:
    kafka:
      topics:
        specTopic: gh-spec <2> 
        statusTopic: gh-status.*  # Topic for agents to report events and status updates
      consumerGroupPrefix: org1_  # Prefix for Kafka consumer groups
    postgres:
      retention: 18m
  availabilityConfig: High  # Deployment replication for availability: Basic or High (default: High)
----

*Configuration parameters:*

* `availabilityConfig`: Specifies deployment replication for improved availability. Options are `Basic` (single replica deployment) and `High` (creates replicas for manager, built-in Kafka, and Grafana components for high availability). The default value is `High`.
* `installAgentOnLocal`: Determines whether to deploy the Global Hub Agent on the local hub cluster. If set to `true`, the Global Hub Agent will be installed on the local hub cluster only. If set to `false`, the Global Hub Agent will not be installed on the local hub cluster. The default value is `true`.
* `specTopic`: The topic to distribute workloads from global hub to managed hubs. The default value is `gh-spec`.
* `statusTopic`: The topic where agents report events and status updates to the manager. The topic can end with an asterisk (\*), indicating topics for individual managed hubs. For example, `gh-status.*` creates topics like `gh-status.hub1` for a hub cluster named `hub1`. In BYO (Bring Your Own) Kafka scenarios, the default value for all managed hubs is `gh-status`.
* `consumerGroupPrefix`: Specifies the prefix for Kafka consumer groups. The final consumer group ID is constructed as `<prefix> + "global_hub"` for Global Hub, and `<prefix> + <managed-hub-name>` for Managed Hubs (hyphens replaced with underscores). If not specified, defaults to hub name only (hyphens replaced with underscores). In the example above, `org1_` is used as the prefix.

The {global-hub} agent is now automatically installed on an existing {acm-short} hub cluster, and you can create a `MultiClusterGlobalHub` custom resource by completing the following procedures: 

* xref:../global_hub/global_hub_install_connected.adoc#global-hub-install-connected[Installing Multicluster Global Hub in a connected environment]
* xref:../global_hub/global_hub_install_disconnected.adoc#global-hub-install-disconnected[Installing Multicluster Global Hub in a disconnected environment]

*Note:* If you enabled the `MultiClusterObservability` custom resource in the {acm-short} after you installed {global-hub}, then any new update for the `MultiClusterObservability` custom resource does not take effect.
