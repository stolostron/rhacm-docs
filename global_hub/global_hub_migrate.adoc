[#global-hub-migrating-managed-clusters]
= Migrating managed clusters

*Technology Preview:* You can access the Managed Cluster Migration feature in {global-hub} 1.5. You can migrate managed clusters from one {acm-short} hub cluster to another and across versions, for example, from {acm-short} 2.13 to {acm-short} 2.14.

By using {global-hub} to migrate your managed cluster, you have a unified process that helps you perform the following actions: 

* Reorganize workloads among {acm-short} hub clusters
* Move clusters and their resources together 
* Automate cluster registration and cleanup 
* Tracks individual steps with detailed status updates 

To fully migrate your managed clusters, complete the following sections: 

. <<prerequisites, Prerequisites>> 
. <<migration-process, Managed cluster migration process>> 
. <<preparing-migration-environment, Preparing the migration environment>> 
. <<migrating-managed-clusters, Migrating managed clusters>> 
. <<tracking-migration-status, Tracking the migration status>> 

[#prerequisites]
== Prerequisites 

To migrate your managed clusters, you need the following components: 

* The {global-hub} operator to organize the migration workflow.
* The `source` {acm-short} hub cluster to manage the clusters and the associated resources. 
* The `target` {acm-short} hub cluster to receive the migrated clusters and the associated resources. 

[#migration-process]
== Managed cluster migration process 

With {global-hub}, you can manage large fleets of clusters by implementing the event-driven architecture of {global-hub}. {global-hub} connects itself to your managed hub clusters. With the {global-hub} event-based design, you can enable {global-hub} to communicate, organize, synchronize, and transfer resources and cluster states among all you hub clusters.  

The manage cluster migration process requires coordination between a `source` and `target` {acm-short} hub cluster. The `multicluster-global-hub-agent` performs the migrations tasks on the `source` and `target` hub clusters. The `multicluster-global-hub-manager` controls the flow of the migration between the `source` and `target` hub clusters and manages the `ManagedClusterMigration` resources. 

During the managed cluster migration, the `source` and `target` hub clusters go through different phases. These phases and their conditions help track the status changes of the hub clusters throughout the migration process. See the following table for an outline of each phase and its condition:  

.Table list of _Phase_ and _Condition_
|===
| Phase | Condition 

| `Pending`
| Performs one migration at a time. Other migrations remain `Pending`. 

| `Validating`
| Verifies that the clusters and hub clusters are valid. 

| `Initializing`
| Prepares the `target` and `source` hub cluster. 

| `Deploying`
| Migrates selected clusters and their resources. 

| `Registering`
| Restarts the registration of the cluster to the `target` hub cluster. 

| `Cleaning`
| Cleans the resources from both `target` and `source` hub cluster and manages the `rollback` if needed. 

| `Completed`
| Confirms the migrations are successfully completed. 

| `Failed`
| Confirms that the migration has failed and includes this failure message in the `status`.  
|===

See the following table for the supported versions and the corresponding {global-hub} `source`, and `target` hub versions: 

.Table list of supported versions 
|===
| {global-hub} version for migration | `source` hub version | `target` hub version

| {global-hub} 1.5
| {acm-short} 2.14
| {acm-short} 2.14

| {global-hub} 1.5
| {acm-short} 2.13
| {acm-short} 2.14
|===


[#preparing-migration-environment]
== Preparing the migration environment 

To prepare your {global-hub} environment for migration, you can create a Brownfield environment by deploying the {global-hub} control plane directly into the `source` hub cluster. Then, you can import the `target` hub cluster into the {global-hub} environment that is in the `Hosted` mode. 

Complete the following steps: 

. Install the {global-hub} operator in the `source` {acm-short} hub cluster. 
. Enable the `local-cluster` in the {global-hub} custom operator that is running in the `source` hub cluster. 
. Apply the following YAML to create the {global-hub} operand and enable the {global-hub} agent to run locally:

+
[source,yaml]
----
apiVersion: operator.open-cluster-management.io/v1alpha4
kind: MulticlusterGlobalHub
metadata:
  name: multiclusterglobalhub
  namespace: multicluster-global-hub
spec:
  availabilityConfig: High
  installAgentOnLocal: true
----
+
. Import the target hub cluster into {global-hub} that is in the `Hosted` mode. Add the following label to the managed hub cluster:

+
[source,bash]
----
global-hub.open-cluster-management.io/deploy-mode=hosted
----

[#migrating-managed-clusters]
== Migrating managed clusters 

After you configure your {global-hub} migration environment, migrate your managed clusters. Complete the following steps to migrate the `cluster1` sample and the associated resources from `hub1` to `hub2` hub clusters:

You can create a `ManagedClusterMigration` resource in the {global-hub} migration environment by directly selecting your managed clusters by name or by using a `Placement` resource. 

To migrate your specific managed clusters by name, complete the following steps: 

. Go to your {global-hub} namespace.
. Apply the following YAML file: 

+
[source,yaml]
----
apiVersion: global-hub.open-cluster-management.io/v1alpha1
kind: ManagedClusterMigration
metadata:
  name: migration-sample
spec:
  from: local-cluster <1>
  includedManagedClusters:
    - cluster1 <2>
    - cluster2
  to: hub2 <3>
----
<1> The `source` hub cluster is a `local-cluster` that {global-hub} installed in `hub1` hub cluster.
<2> The managed clusters that are being migrated to `hub2` hub cluster. The managed cluster in `hub1` and `hub2` hub clusters must be different from one another.
<3> The `target` hub cluster is `hub2`.

To migrate your managed clusters with the `Placement` resource, complete the following steps:

. Go to your {global-hub} namespace.
. Select clusters based on labels, cluster properties, or other criteria defined in your `Placement` resource. 
. Apply the following YAML file: 

+
[source,yaml]
----
apiVersion: global-hub.open-cluster-management.io/v1alpha1
kind: ManagedClusterMigration
metadata:
  name: migration-placement-sample
spec:
  from: local-cluster <1>
  includedManagedClustersPlacementRef: production-clusters <2>
  to: hub2 <3>
----
<1> The `source` hub cluster is a `local-cluster` that {global-hub} installed in `hub1` hub cluster.
<2> The `Placement` resource that has the name `production-clusters` and that defines which clusters get migrated. You must define the `Placement` resource in the {global-hub} agent namespace of the source hub cluster. For example, you can name the `Placement` resource `multicluster-global-hub` or `multicluster-global-hub-agent`.
<3> The `target` hub cluster is `hub2`.

. Specify the `includedManagedClusters` or `includedManagedClustersPlacementRef` cluster type to include in your migration. Include only one of these cluster types in your migration because they cannot exist together. 

[#tracking-migration-status]
== Tracking the migration status

During the migration process, you can track the statuses of your managed clusters by using the {global-hub} `ConfigMap` or the migration customer resource. 

{global-hub} automatically creates a `ConfigMap` which gives you a detailed cluster list, telling you if the cluster migration fails or succeeds. The migration customer resources gives you the status of the entire migration process. 

Track the migration status of your managed clusters by completing the following steps:

. View the migration status from the `ConfigMap` by running the following command:

+
[source,bash]
----
kubectl get configmap <migration-name> -n <global-hub-namespace> -o yaml
----
+
. Ensure that the `ConfigMap` that you see resembles the following sample: 

+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: migration-sample
  namespace: multicluster-global-hub
data:
  success: '["cluster1","cluster3"]'
  failure: '["cluster2"]'
----
+
. To view the tracking status from the migration customer resource, verify that its migration status is `True`, and that it resembles the following sample: 

[source,yaml]
----
status:
  conditions:
    - type: ResourceValidated
      status: "True"
      message: Migration resources have been validated
    - type: ResourceInitialized
      status: "True"
      message: All source and target hubs have been initialized
    - type: ResourceDeployed
      status: "True"
      message: Resources have been successfully deployed to the target hub cluster
    - type: ClusterRegistered
      status: "True"
      message: All migrated clusters have been successfully registered
    - type: ResourceCleaned
      status: "True"
      message: Resources have been successfully cleaned up from the hub clusters
  phase: Completed
----
