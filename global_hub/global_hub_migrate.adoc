[#global-hub-migrating-managed-clusters]
= Migrating managed clusters (Technology Preview)

With {global-hub}, you can migrate managed clusters from one {acm} hub cluster to another and migrate associated Kubernetes resources, such as, `ConfigMaps` and `Secrets`. 

By using {global-hub} to migrate your managed cluster, you have a unified process that helps you perform the following actions: 

* Reorganize workloads among {acm-short} hub clusters. 
* Move clusters and their resources together. 
* Automate cluster registration and cleanup. 
* Tracks individual steps with detailed status updates. 

To fully migrate your managed clusters and to understand the process, complete the following sections: 

. <<understanding-migration, Understanding the managed cluster migration process>> 
. <<understanding-imported-hub-clusters, Understanding the imported hub clusters>> 
. <<installing-brownfield-environment, Installing a Brownfield environment>> 
. <<migrating-managed-clusters, Migrating managed clusters>> 

[#understanding-migration]
== Understanding the managed cluster migration process 

With {global-hub}, you can manage large fleets of clusters by implementing the event-driven architecture of {global-hub}. Because of this architecture, {global-hub} connects to your managed hub clusters. With the managed cluster migration, you can also implement {global-hub} to communicate, organize, synchronize, and transfer resources among all you hub clusters. 

The manage cluster migration process requires coordination between a `source` hub and `target` {acm-short} hub. The `multicluster-global-hub-agent` performs the migrations tasks on the `source` and `target` hubs. The `multicluster-global-hub-manager` controls the flow of the migration between the `source` and `target` hub and manages the `ManagedClusterMigration` resources. 

During the managed cluster migration, the `source` and `target` hubs go through different phases. These phases and their conditions help track the status changes of the hubs throughout the migration process. See the following table for an outline of each phase and its condition:  

.Table list of _Phase_ and _Condition_
|===
| Phase | Condition 

| `Pending`
| Performs one migration at a time. Other migrations remain `Pending`. 

| `Validating`
| Verifies that the clusters and hub clusters are valid. 

| `Initializing`
| Prepares the `target` hub and `source` hub. 

| `Deploying`
| Migrates selected clusters and their resources. 

| `Registering`
| Restarts the registration of the cluster to the `target` hub. 

| `Cleaning`
| Cleans the resources from both `target` and `source` hub and manages the `rollback` if needed. 

| `Completed`
| Confirms the migrations has successfully completed. 

| `Failed`
| Confirms that the migration has failed and includes this failure message in the `status`.  
|===

*Note:* The `Validating` phase does not check resources such as `ConfigMap` and `Secret`. If you specify resources that do not exist in the `source` hub, the migration fails in the `Deploying` phase. 

[#understanding-imported-hub-clusters]
== Understanding the imported hub clusters 

When you import a {acm-short} hub into the {global-hub} agent, you must add the label, `global-hub.open-cluster-management.io/deploy-mode`. With this label, you indicate that the hub is a managed cluster hub. Without this label, you cannot install the {global-hub} agent. 

The label, `global-hub.open-cluster-management.io/deploy-mode` supports the following values: 

* `default`: Use this value when the {acm-short} hub cluster that is imported does not have self-management enabled. With this value, the `Klusterlet` and {global-hub} agent install directly in the imported {acm-short} hub cluster.    
* `hosted`: Use this value when the {acm-short} hub cluster that is imported does have self-management enabled. Only use this value if the {global-hub} cluster also has self-management enabled and if the `kubeconfig` of the imported {acm-short} hub cluster does not expire. 

[#installing-brownfield-environment]
== Installing a Brownfield environment 

By installing a Brownfield environment in your {global-hub} operator, you can more easily migrate managed clusters. To install a Brownfield environment, complete the following steps: 

. Install the {global-hub} agent on the `source` hub.  
. Enable the {global-hub} agent in a Brownfield environment by applying the following YAML in the `source` hub: 

+
[source,yaml]
----
  apiVersion: operator.open-cluster-management.io/v1alpha4
  kind: MulticlusterGlobalHub
  metadata:
    name: multiclusterglobalhub
    namespace: multicluster-global-hub
  spec:
    availabilityConfig: High
    installAgentOnLocal: true
    featureGates:
    - feature: ImportClusterInHosted
      mode: Enable
----

[#migrating-managed-clusters]
== Migrating managed clusters 

After installing a Brownfield environment, migrate your managed clusters by importing them in the `Hosted` mode. 

Complete the following steps: 

. Import the managed hub in a `Hosted` mode by giving `hub2` the following label:  `global-hub.open-cluster-management.io/deploy-mode=hosted`. 
. To move the cluster and its related resources, define the `ManagedClusterMigration` by applying the following YAML: 

+
[source,yaml]
----
apiVersion: global-hub.open-cluster-management.io/v1alpha1
kind: ManagedClusterMigration
metadata:
  name: migration-sample
spec:
  from: local-cluster <1>
  includedManagedClusters: <2> 
    - cluster1
  includedResources: <3> 
    - configmap/default/foo
    - secret/cluster1/bar
  to: hub2 <4> 
----
<1> The `source` hub which is the `hub1`. 
<2> The `target` hub which is the `hub2`. 
<3> Lists the clusters to be migrated and includes unique cluster names for both `hub1` and `hub2`. 
<4> Specifies the Kubernetes resources to migrate by using the format, `kind/namespace/name`. 

. In the `status` resource section, verify that your migration status resembles the following status: 

+
[source,bash]
----
status:
  conditions:
    - type: ResourceValidated
      status: "True"
      message: Migration resources have been validated
    - type: ResourceInitialized
      status: "True"
      message: All source and target hubs have been initialized
    - type: ResourceDeployed
      status: "True"
      message: Resources have been successfully deployed to the target hub cluster
    - type: ClusterRegistered
      status: "True"
      message: All migrated clusters have been successfully registered
    - type: ResourceCleaned
      status: "True"
      message: Resources have been successfully cleaned up from the hub clusters
  phase: Completed
----
