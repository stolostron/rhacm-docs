[#upgrade-considerations]
=  Upgrade considerations for your hub cluster

[role="_abstract"]
Before you upgrade of your {acm} hub cluster, see the following information about the upgrade process and requirements, then proceed to xref:./upgrade_hub.adoc#upgrading-hub[Upgrading your hub cluster] for instructions about how to upgrade your hub cluster.

*Required access:* {ocp-short} administrator

* Plan to upgrade both {acm-short} and {mce-short}. Do not attempt to upgrade {mce-short} separately from {acm-short} upgrade because this action can cause issues with your cluster.

* If you attempt to upgrade to an unsupported {ocp-short} version, you receive an error message. If you force the upgrade to an _unsupported_ version, your {acm-short} hub cluster does not function correctly.

* When you upgrade {acm-short}, {mce-short} automatically upgrades to the required version. The `MultiClusterHub` `mceVersionCompliance` resource status is `isCompliant: true`. 

* Upgrades are always supported from the immediate previous version. You can upgrade to the next available feature release. 

* If you are on a version with _Extended Update Support_ (EUS), you can upgrade to the next version, or you can skip to the next EUS version. You can perform skip-level upgrades from `<2.x>` to `<2.x+2>` on _odd_ number versions of {acm-short}. For instance, when you upgrade {acm-short} 2.13, which is an EUS version, you can choose to upgrade to version 2.15, which is also an EUS version.

* Downgrading a version is not supported. You cannot revert to an earlier version after upgrading to a later version in the channel selection. You must uninstall the operator and reinstall it with the earlier version to use a previous version.

* The {olm} `operatorcondition` helps control how versions are upgraded. When you initially deploy {acm-short} by using the operator, you make the following selections:

+
Channel:: Channel corresponds to the version of the product that you are installing. The initial channel setting is often the most current channel that was available at the time of installation. 
Approval:: Approval specifies whether approval is required for updates within the channel, or if they are done automatically. 

+
* If set to `Automatic`, then minor release updates in the selected channel are deployed without administrator intervention. 
+
- If set to `Manual`, then each update to the minor release within the channel requires an administrator to approve the update. 
+
You also use these settings when you upgrade to the latest version of {acm-short} by using the operator. Continue to xref:./upgrade_hub.adoc#upgrading-hub[Upgrading your hub cluster] to complete the steps to upgrade your operator.

* Component considerations

** If you are link:../clusters/cluster_lifecycle/cluster_pool_intro.adoc#managing-cluster-pools[Managing cluster pools (Technology Preview)], you need further configuration to stop automatic management of these cluster pools after upgrade. Set `cluster.open-cluster-management.io/createmanagedcluster: "false"` in the `ClusterClaim` `metadata.annotations`. 

** If you use {gitops-short}, verify that the `managedserviceaccount` component is enabled in {mce-short} before you upgrade. {gitops-short} uses short-lived tokens that require this component. If the component is disabled, {gitops-short} loses connectivity to managed clusters and Argo CD applications show as `Unknown`. See link:../clusters/install_upgrade/adv_config_install.adoc#serviceaccount-addon[ManagedServiceAccount add-on] and link:../gitops/gitops_registering.adoc#gitops-register[Registering managed clusters to {gitops} operator].
