= Enabling {gitops} add-on with Argo CD Agent (Technology Preview)

[role="_abstract"]
Use `Agent` mode for the pull model to enable the {gitops-short} add-on and receive application health statuses. This mode is for environments with network restrictions, enhanced security requirements, or when implementing a pull model for application delivery. The `Advanced` pull model uses the Argo CD Agent to deliver a fully automated {gitops-short} experience.

*Required access:* Cluster administrator

.Prerequisites

* {acm-short} hub cluster installed.
* Managed clusters registered with {acm-short}.
* {gitops-short} operator installed on the hub cluster.
* A `Placement` resource to select target managed clusters.
* `ManagedClusterSet` bound to the target namespace.
* {gitops-short} operator subscription configured with the Argo CD Agent environment.
* The `ArgoCD` custom resource is configured for the `Agent` mode. For more information see xref:../gitops/gitops_configure.adoc#configure-subs-resources-gitops[Configuring subscriptions and resources for Argo CD].

.Procedure 

Create a `GitOpsCluster` resource to manage the Argo CD Agent add-on deployment. The `GitOpsCluster` controller performs automated PKI management and deploys the Argo CD Agent on each selected managed cluster. To enable the advanced pull model for Argo CD Agent architecture, complete the following steps:

. On your hub cluster, create a `GitOpsCluster` resource with the Argo CD Agent enabled by adding the following YAML sample: 

+
[source,yaml]
----
apiVersion: apps.open-cluster-management.io/v1beta1
kind: GitOpsCluster
metadata:
  name: gitops-agent-clusters
  namespace: openshift-gitops
spec:
  argoServer:
    argoNamespace: openshift-gitops
  placementRef:
    kind: Placement
    apiVersion: cluster.open-cluster-management.io/v1beta1
    name: production-clusters
    namespace: openshift-gitops
  gitopsAddon:
    enabled: true
    argoCDAgent:
      enabled: true
      mode: managed
----
+
*Notes:* 

- The `mode` field determines the agent operation mode. The default value is `managed`. If you want to change the mode to `autonomous`, set the `mode` field to `autonomous` in the `argoCDAgent` specification. The only valid values are `managed` and `autonomous`. For more information about agent operation modes, see the {gitops-short} documentation.

- For {ocp-short} managed clusters, you can enable OLM-based deployment by adding `olmSubscription.enabled: true` to the `gitopsAddon` specification in case the add-on auto-detection of the cluster type is not working properly. For more information, see xref:../gitops/gitops_manage_addon.adoc#manage-gitops-addon[Managing the {gitops} add-on].

. Apply the YAML sample by running the following command:  

+
[source,bash]
----
oc apply -f gitopscluster-example.yaml
----

. The controller automatically discovers the Argo CD Agent principal server address from the {ocp-short} Route. Verify the discovered address by running the following command:

+
[source,bash]
----
oc get gitopscluster gitops-agent-clusters -n openshift-gitops -o jsonpath='{.spec.gitopsAddon.argoCDAgent.serverAddress}'
----

+
*Note:* If you need to override auto-discovery for non-standard setups, you can manually specify `serverAddress` and `serverPort` in the `argoCDAgent` specification.

. Create an application on the hub cluster and confirm it works on the managed cluster to verify the completion of the advanced `Pull Model` workflow. To verify the necessary installations and resources for successful deployment, complete the following steps:

.. Check the `GitOpsCluster` status for specific `Agent` conditions by running the following command:

+
[source,bash]
----
oc get gitopscluster gitops-agent-clusters -n openshift-gitops -o jsonpath='{.status.conditions}' | jq
----

+
See the following condition types in the status:

+
`Ready`:: The `GitOpsCluster` is ready and all the components are functioning. 
`PlacementResolved`:: The `Placement` reference is resolved and the managed clusters are retrieved. 
`ClustersRegistered`: The managed clusters are successfully registered with  the `ArgoCD` server.
`AddOnDeploymentConfigsReady`:: The `AddOnDeploymentConfigs` are created for all the managed clusters.
`ManagedClusterAddOnsReady`:: The `ManagedClusterAddons` creates and updates the managed clusters. 
`AddOnTemplateReady`:: The dynamic `AddOnTemplate` created for the Argo CD Agent mode. 
`ArgoCDAgentPrereqsReady`:: The agent prerequisites are set up.
`CertificatesReady`:: The TLS certificates are signed.
`ManifestWorksApplied`:: The CA certificates propagated to managed clusters.
`ArgoCDPolicyReady`:: The `ArgoCD` `Policy` is created for managing the `ArgoCD` custom resource on managed clusters.

.. Verify the agent principal is running on the hub cluster by running the following command:

+
[source,bash]
----
oc get pods -n openshift-gitops -l app.kubernetes.io/name=openshift-gitops-agent-principal
----

.. Deploy applications by using an `ApplicationSet` resource on the hub cluster. In agent mode, use `destination.name` so the principal routes the application to the correct agent. See the following YAML sample:

+
[source,yaml]
----
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-appset
  namespace: openshift-gitops
spec:
  generators:
  - clusterDecisionResource:
      configMapRef: acm-placement
      labelSelector:
        matchLabels:
          cluster.open-cluster-management.io/placement: <app-placement-name>
      requeueAfterSeconds: 30
  template:
    metadata:
      name: '{{name}}-guestbook'
    spec:
      project: default
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps
        targetRevision: HEAD
        path: guestbook
      destination:
        name: '{{name}}'
        namespace: guestbook
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
        - CreateNamespace=true
----

+
*Note:* The `destination.name: '{{name}}'` field uses destination-based mapping so the principal routes applications to the correct agent. The `configMapRef: acm-placement` references the duck-type `ConfigMap` that the `GitOpsCluster` controller creates automatically.

.. Apply the YAML sample by running the following command:

+
[source,bash]
----
oc apply -f applicationset.yaml
----

.. On the managed cluster, verify the agent is running by running the following command:

+
[source,bash]
----
oc get pods -n openshift-gitops -l app.kubernetes.io/part-of=argocd-agent --context <managed-cluster-context>
----

.. On the hub cluster, verify that the application status shows `Synced` by running the following command:

+
[source,bash]
----
oc get applications.argoproj.io -n openshift-gitops
----
